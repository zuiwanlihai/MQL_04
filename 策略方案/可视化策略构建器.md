# 可视化策略构建器分析

## 总体判断

当前项目已有可用的可视化策略构建器，但它本质上是一个**线性积木配置器 + Python 代码生成器**，不是通用的拖拽流程图，也不是完整的无代码风控策略平台。

它适合快速生成单品种、指标条件驱动的基础策略；不支持直接搭建网格、组合仓位、止损/熔断等更复杂策略。整体实现链路已打通，但手工改代码后的配置一致性和保存可靠性值得优先检查。

## 当前能力

- 支持 MA、EMA、RSI、BOLL、ATR、MACD 六类指标；条件支持上穿、下穿、大于、小于，操作数可选指标输出、收盘价或数值常量。见 [构建器积木定义](../frontend/src/lib/builder/types.ts)。
- 可设置品种、周期、固定手数及做多/做空方向；可配置多个规则并排序。
- 左侧积木面板通过点击添加，画布中的指标和规则可拖动排序；右侧 Monaco 实时展示生成代码。见 [构建器页面](../frontend/src/pages/Strategies/BuilderPage.tsx)。
- 代码生成器生成纯 Python 策略回调，计算指标、取历史 K 线、判断条件并调用交易 API；交叉条件会比较当前与前一根 K 线。见 [代码生成器](../frontend/src/lib/builder/codegen.ts)。
- 创建策略时把生成源码和 `builder_config` 一起保存；后续可从积木配置恢复编辑。后端通过 `strategies.builder_config` JSONB 字段保存配置，详情接口读回。见 [策略模型](../backend/app/models/strategy.py) 和 [策略接口](../backend/app/api/v1/endpoints/strategies.py)。
- 已有代码生成器单测，覆盖指标、条件、方向限制、动作和配置校验；后端测试覆盖配置存取。见 [代码生成器测试](../frontend/src/lib/builder/codegen.test.ts) 和 [构建器 API 测试](../backend/tests/test_strategy_builder_api.py)。

## 主要限制

1. **交易逻辑范围较窄**：构建器有指标、比较条件和开平动作，但没有止损、止盈、移动止损、最大持仓时长、资金比例仓位、回撤熔断或冷却机制。生成策略默认固定手数，并且开仓仅在当前没有持仓时执行，实质上更接近“一次一仓”。
2. **不是完整的无代码拖拽画布**：从面板点击添加，再拖动画布里的积木排序；规则按列表顺序逐项处理，不提供通用流程分支、AND/OR 条件组或复杂状态机。
3. **移动端难以使用**：指标面板和代码预览均使用 `hidden md:flex`；窄屏时积木面板不可见，空配置又无法先添加指标，构建流程会受限。相关布局在 [BuilderPage](../frontend/src/pages/Strategies/BuilderPage.tsx) 中。
4. **服务端对 DSL 的校验较弱**：后端将 `builder_config` 作为普通字典存取，并不校验其字段结构或规则引用完整性。主要配置校验在前端代码生成器中执行。
5. **保存不是原子操作**：编辑现有策略时先保存源码，再单独更新元数据和 `builder_config`。若第一步成功而第二步失败，源码与积木配置可能不一致。当前保存源码调用还传入 `base_updated_at: null`，没有使用乐观并发保护。见 [BuilderPage](../frontend/src/pages/Strategies/BuilderPage.tsx)。
6. **手工修改后的配置可能过期**：手工编辑源码时，后端只更新 `source_code`，没有清除或标记 `builder_config`。构建器的覆盖提醒只在 `builder_config` 为空时出现；如果源码被手动改过但旧配置仍在，重新进入构建器可能加载旧积木，保存时覆盖源码而没有相应提醒。见 [保存源码接口](../backend/app/api/v1/endpoints/strategies.py) 和 [构建器覆盖提醒](../frontend/src/pages/Strategies/BuilderPage.tsx)。
7. **测试偏重纯函数**：代码生成器和 API 配置存取有测试，但当前看到的覆盖重点不是浏览器交互、整条构建—保存—校验—回测流程，也没有证明生成策略的交易表现。

## 建议优先级

### 优先修复数据一致性和保存安全

- **把构建器保存收敛为单个原子 API 操作。**建议增加构建器专用保存接口，一次提交 `source_code`、`builder_config`、`symbol_ids`、`timeframe`、`direction` 和 `base_updated_at`，在同一数据库事务内校验并更新；避免目前先调用源码保存、再调用策略元数据更新导致部分成功。源码、构建器配置和策略元数据应一起成功或一起失败。
- **启用乐观并发控制。**构建器编辑时保留详情响应中的 `updated_at`，保存时提交 `base_updated_at`；发生 409 冲突时提示用户刷新/比较，不要静默覆盖其他窗口的修改。不要以 `null` 关闭并发检查。
- **检测源码与 DSL 是否脱离。**构建器保存时记录生成源码的 SHA-256 摘要；手工源码编辑后，若源码摘要与最近生成摘要不同，应将构建配置标记为“已脱离”，重新进入构建器时明确提示：继续编辑将以积木生成代码覆盖当前源码。让用户选择继续覆盖、返回编辑器或另存为副本。版本恢复等其他改变源码的入口也应更新脱离状态。
- **先做后端结构校验，再持久化。**将当前 `dict` 字段收敛为版本化 DSL schema：验证版本号、允许的指标/操作符/操作数、数值范围、唯一 ID、指标引用和方向/动作兼容性；对未知版本返回明确的 422，而不是保存后等前端生成失败。
- **校验生成源码。**服务端从 DSL 生成源码或核对提交的源码与 DSL 一致，并运行现有 AST 策略校验；有 error 级结果时拒绝保存，warning 级结果展示给用户。验证时不能把静态 AST 检查误当成沙箱安全边界，运行仍须经过现有策略沙箱。
- **覆盖前设置明确确认。**对于已有策略，展示将覆盖的目标源码/参数范围，并要求用户确认；建议支持“另存为新策略”，避免试错直接覆盖工作副本。

### 随后完善产品可用性

- **明确规则执行语义。**说明规则按列表顺序逐条检查，规定同一根 K 线多条规则同时触发、先平后开、已有持仓和订单失败时的行为；如条件组合仍采用线性列表，应在 UI 中说明，不要暗示支持任意流程图。后续需要 AND/OR 时，先扩展 DSL 和版本迁移规则，再扩展 UI 和代码生成器。
- **扩充策略积木时采用可审计的分阶段范围。**第一阶段考虑止损/止盈、最大持仓数、最长持仓及固定/按风险比例的仓位模式；第二阶段再考虑移动止损、日亏损/回撤熔断和冷却。每种积木要定义输入单位、触发价格、检查时机、订单失败行为及回测表现，并对账户级约束标注“策略级”或“账户级”。在账户级风控未接通之前，不应将策略内积木称为全账户保护。
- **改善窄屏和键盘可用性。**目前指标添加面板与代码预览在小屏隐藏；应提供移动端可访问的“添加指标/规则”入口、可切换的代码预览面板，并支持键盘操作及拖动之外的上移/下移按钮。若不支持手机编辑，应明确显示桌面端提示，不要留下无法继续的空白画布。
- **增强校验和错误定位。**将校验分为 DSL 字段校验、代码生成校验、后端 AST 校验和策略运行前检查；错误信息标明对应的指标/规则卡片及字段。对品种/周期等插入 Python 源码的值进行枚举或格式校验，并用安全的字符串序列化方式生成源码。
- **完善保存状态提示。**区分“未保存”“保存中”“已保存”“冲突”“服务端校验失败”；保存失败时保留画布配置和生成代码，不显示成功状态。

### 测试与发布门禁

- **DSL 单测：**合法配置、未知版本、非法数值、重复 ID、悬空引用、不支持的指标输出、方向冲突、极端参数和特殊字符串。
- **生成器测试：**每类积木的代码快照、足够/不足预热数据、多个同时触发的规则、先平后开、各方向限制、生成源码可解析且通过策略 AST 校验。
- **API 测试：**创建和更新原子性、源码/DSL 摘要一致、手工源码更新后脱离状态、乐观锁冲突、archived 策略拒绝更新、非法 DSL 返回 422。
- **前端组件/E2E：**新建、保存、退出重进还原、规则排序、覆盖确认、手工修改后警示、并发冲突、保存失败时保留草稿、窄屏操作。
- **策略行为验证：**把生成策略送入已有 Paper/Backtest 引擎，验证信号触发与实际成交/持仓一致；代码生成测试通过不等于策略盈利或风险已验证。
- 发布前执行前端类型检查与构建、相关 Vitest、后端策略 API 测试，以及一条从构建器创建到回测报告的端到端验证。

## 推荐实施顺序

| 阶段 | 范围 | 完成标准 |
|---|---|---|
| P0：保护数据 | 原子保存接口、乐观锁、源码/DSL 脱离检测、覆盖确认 | 任一保存失败都不产生部分更新；手工改源码后构建器不会静默使用旧配置覆盖。 |
| P1：服务端可信校验 | 版本化 DSL schema、源码生成/一致性检查、AST 校验 | 非法配置或生成源码无法通过校验时，服务端拒绝保存并返回可定位错误。 |
| P2：执行语义与体验 | 规则优先级说明、窄屏/键盘可用性、校验定位 | 新手能理解多规则执行顺序；桌面与窄屏均可完成配置和保存，错误能定位到规则。 |
| P3：风控能力 | 止损、止盈、仓位、最长持仓、熔断积木分步实现 | 每个风控块具备明确单位、运行时行为、模拟/回测覆盖和限制说明；账户级风控须接入账户数据后才标为账户级。 |
| P4：发布验证 | API、前端、回测 E2E 和样本外策略验证 | 创建、保存、恢复、校验、运行链路通过；策略绩效单独报告，不从代码测试推断。 |

## 结论

建议先处理 **P0 数据保护**，再做 **P1 服务端校验**；在保存安全和生成结果可验证之前，不建议先扩充大量新积木。后续按 P2–P4 分阶段交付，并保持“策略级能力”和“账户级保护”的清晰边界。

构建器目前已具备“配置 → 生成 Python → 保存策略”的基础闭环，适合作为简单指标策略的起步工具；在完成保存一致性、服务端校验、运行语义和风控验证之前，不宜把它视为完整的生产级无代码策略系统。
