## 1. 产品概述

### 1.1 背景与问题

MetaTrader 5（MT5）是全球外汇/CFD 零售交易的主流终端，但原生 MT5 存在明显痛点：

| 痛点 | 说明 |
|---|---|
| 策略开发门槛高 | MQL5 语言小众，调试体验差，缺少现代 IDE 能力 |
| 无法 Web 化协作 | 策略、回测、监控全部锁死在 Windows 桌面终端里 |
| 数据使用不便 | 历史数据导出/清洗繁琐，难以与 Python 生态（pandas、机器学习）结合 |
| 回测能力割裂 | MT5 策略测试器功能强但结果难对比、难共享、难做组合级回测 |
| 风控薄弱 | 缺少账户级统一风控、异常熔断、多渠道告警 |

### 1.2 产品定位

**一句话定位**：一个基于浏览器的量化交易工作台，以 MT5 为数据源与执行通道，覆盖「数据 → 策略研发 → 回测 → 模拟 → 实盘 → 风控监控」的完整闭环。

- **形态**：Web 应用（B/S 架构），后端通过 MT5 网关节点连接券商终端
- **阶段假设**：Phase 1 面向个人/小团队私有化部署（单租户）；架构预留多租户能力，Phase 3 可演进为 SaaS
- **不做**：不做券商、不做资管募集、不提供投资建议/信号售卖（合规红线）

### 1.3 价值主张

1. **零安装**：打开浏览器即可研究行情、写策略、跑回测、看实盘
2. **Python 优先**：策略用 Python 编写，无缝对接 pandas / numpy / sklearn 生态
3. **回测即可信**：基于 MT5 真实历史数据（含点差/滑点/隔夜费建模），回测-模拟-实盘三态一致
4. **风控兜底**：事前风控检查 + 一键熔断，实盘资金安全优先于一切功能

### 1.4 成功指标（North Star & KPI）

| 指标 | MVP 目标（上线后 3 个月） |
|---|---|
| 北极星指标 | 每周完成「回测→模拟/实盘」转化的策略数 |
| 回测任务成功率 | ≥ 99% |
| 回测延迟（1 年 M1 数据、单品种） | ≤ 30 秒 |
| 实盘下单链路延迟（信号→MT5 发单） | ≤ 200ms（局域网网关） |
| 风控拦截准确率 | 误拦率 < 0.1%，漏拦率 0 |

## 2. 用户分析

### 2.1 目标用户画像

**P1 - 个人量化交易者「老周」**
- 35 岁，有 MT5 实盘账户，会 Python 基础，厌倦了在 MT5 里手写 MQL
- 诉求：用 Python 写策略、快速验证想法、上班时用手机/网页盯盘
- 付费意愿：为省时间付费，接受私有化部署或月订阅

**P2 - 策略开发者/工作室「阿凯」**
- 全职做策略，同时管理 3~10 个 MT5 账户（多券商）
- 诉求：批量回测、参数优化、多账户统一监控与风控、告警到 Telegram
- 关键特征：重度用户，决定产品口碑

**P3 -（远期）SaaS 租户**
- 小型资管/IB 代理，需要给下属或客户分配权限、隔离数据

### 2.2 核心用户旅程（老周）

```
注册/登录 → 绑定 MT5 账户(网关授权) → 浏览行情数据 → 新建 Python 策略
→ 配置回测(品种/周期/资金/点差) → 查看回测报告(权益曲线/回撤/夏普)
→ 参数优化找到满意参数 → 部署到模拟盘 → 连续运行≥14天通过准入闸门 → 切到实盘(设风控限额, 进入观察期)
→ 每日看监控面板/收告警 → 月度复盘报告
```

### 2.3 竞品参照

| 竞品 | 可借鉴 | 我们的差异 |
|---|---|---|
| TradingView | 图表体验、Pine 编辑器即时回测 | 深度对接 MT5 实盘执行 + Python 生态 |
| QuantConnect | 研究/回测/实盘一体化流程 | 专注 MT5/外汇 CFD 场景，轻量私有化部署 |
| vn.py / FMZ | 开源生态、多平台接入 | Web 化开箱即用，无需自己搭环境 |
| MT5 原生策略测试器 |  tick 级真实数据回测 | 复用其数据源，但提供现代 UI 与组合分析 |

### 3.1 模块详述（仅展开 P0 关键需求）

#### M1 MT5 网关绑定与常驻运维
- **功能**：用户在「接入管理」页添加 MT5 账户（MVP 仅单账户，多账户管理 P1）：填写网关地址 → 输入 MT5 账号/密码/服务器 → 测试连接 → 绑定成功显示账户信息（余额、杠杆、券商名）
- **规则**：
  - 密码传输全程 TLS，落库加密（AES-GCM + KMS 密钥），仅网关节点内存中解密使用
  - 支持「只读模式」（仅取数据，禁交易）与「交易模式」两级授权
  - 网关心跳 5s 一次，断线 30s 内在界面标红并触发告警
- **异常**：账号错误 / 服务器不可达 / 终端未登录 / 版本不匹配，均需给出明确可操作的错误提示；网关掉线 / MT5 终端退出除告警外，告警消息必须附带排障指引入口（跳转一键自检页，逐项给出检查与修复步骤），不得只报状态
- **网关常驻与本地运维（P0，降低自部署模式的运维负担）**

  > **设计前提**：自部署模式要求用户的 Windows 机器常开、MT5 终端保持登录（结构性约束，见 §5.1）。产品目标是把「保持网关活着」压缩到接近零运维，而不是假设用户具备运维能力。

  - **服务常驻**：网关安装即注册为 Windows 服务——开机自启、进程崩溃自动拉起（看门狗 30s 内重启）；连续拉起失败 ≥ 3 次 → 停止重试并告警等待人工介入（避免无限抖动）
  - **终端守护**：网关监测 MT5 终端进程与登录态，终端崩溃/掉登录时自动拉起；系统开机后等待终端就绪再恢复服务
  - **电源管理**：实盘运行前检查 Windows 电源方案（睡眠/休眠/合盖行为），非常驻供电时**显著警告**并提供一键修复指引；网关监测系统睡眠/恢复事件，唤醒后自动健康自检并通知
  - **一键自检**：健康检查清单页——终端登录 / 券商服务器可达 / 电源方案 / 网关版本 / 系统时间同步，逐项可修复、修复后一键复检
  - **异常重启提示**：网关任何一次异常重启都必须界面显著提示 + 触发告警，文案必须包含「请先核对持仓是否完整」——崩溃期间交易状态可能已变化，不得静默恢复

#### M2 数据中心
- **功能**：
  - 品种树（外汇/金属/指数/加密货币，按券商 symbol 分组），搜索、收藏
  - 实时报价表格：买/卖价、点差、涨跌、更新时间
  - K 线图：M1~MN 全周期，主图叠加 MA/BOLL，副图 MACD/RSI/KDJ；支持画线工具（P1）
  - 历史数据管理：显示每个品种已缓存的数据范围，手动触发补数；后台定时增量同步
- **规则**：数据以 MT5 网关为唯一权威来源；平台缓存仅加速查询，缓存与终端不一致时以终端为准并提供「强制重同步」

#### M3 策略研发（Web Python 编辑器）
- **功能**：
  - Monaco 编辑器：语法高亮、自动补全（平台 SDK）、模板库（双均线、网格、突破等 5 个起步模板）
  - 策略结构约定（事件驱动骨架）：
    ```python
    def on_init(ctx):        # 初始化：声明品种、周期、参数
        ...
    def on_bar(ctx, bar):    # 每根K线回调：信号逻辑
        ...
    def on_order(ctx, order):# 成交回报回调
        ...
    def on_stop(ctx, reason):# 可选：平台停止策略时的收尾
        ...
    ```
  > MVP 仅 bar 驱动：不提供 `on_tick` 回调（tick 级能力随 Tick 数据管理于 P1 引入）
  - **SDK 能力边界（P0，白名单制——未授予即禁止）**

    > **边界的定义方式**：由 **能力面 / 职责面 / 隔离面 / 运行面 / 一致性面 / 演进面** 六个正交维度共同构成。每一维度都必须回答三个问题——*什么被授予、什么被拒绝、越界时如何处置*。三者缺一，边界即不成立。
    > **封闭集合原则**：本 PRD 中出现的所有清单（指标、模块、错误码）均为**封闭集合**，「等 / …」不构成授权；新增能力只能通过本文档或《SDK v1 API 规范》显式追加，不因"同类"而自动授予。

    **① 能力面：SDK v1 授予的 API 面（封闭清单）**

    | 类别 | 授予的能力 | 硬边界 |
    |---|---|---|
    | 行情数据 | 当前/历史 K 线、买卖报价、品种属性（点值 `point` / 手数步长 / 最小最大手数 / 保证金率 / 合约大小） | 历史回看窗口 ≤ 5000 根；仅可访问策略已声明的品种；**只能访问当前 bar 及更早的数据**（见 ⑤） |
    | 交易指令 | 市价开仓 / 平仓 / 减仓（`ctx.buy` / `ctx.sell` / `ctx.close`） | MVP 仅市价单，**且不提供券商侧止损止盈**（见 ②）；减仓以手数（非比例）指定；单根 K 线内下单调数上限默认 20 |
    | 账户信息 | 余额、净值、可用保证金、当前持仓、账户货币、杠杆 | **只读，且仅限策略所绑定的账户**；跨账户访问 = 严重越权，按 ③ 处置 |
    | 指标计算 | 内置指标库 v1（封闭清单）：`SMA` / `EMA` / `WMA` / `MACD` / `RSI` / `KDJ` / `BOLL` / `ATR` / `CCI` / `ADX` / `OBV` | 纯函数，无状态；清单之外的指标由策略用 `numpy` 自行实现 |
    | 状态持久化 | `ctx.storage` 键值存储（跨 bar、跨重启保留） | 配额 ≤ 1MB；**用于替代**文件读写需求；超配额处置见 ④；**重启恢复契约**：策略停止后重启，仅 `ctx.storage` 恢复——普通内存变量不保证恢复，由策略在 `on_init` 中自行重建（三态一致） |
    | 日志 | `ctx.log.info/warn/error` 与 `print` | 二者**同源同契约**：`print` 等价于 `ctx.log.info`，共用同一限速池（≤100 条/秒）；回测日志进报告，实盘日志进运行页 |
    | 时间 | `ctx` 暴露的 bar / 成交时间戳；`datetime` 的构造与运算 | 统一为 **UTC**（见 ⑤）；**不授予真实时钟**（见 ③） |
    | 运行环境标识 | `ctx.mode`（backtest / paper / live） | 仅供日志与防御性判断；产品导向**不鼓励**按模式分叉逻辑（破坏三态一致） |
    | 生命周期回调 | `on_init` / `on_bar` / `on_order` / `on_stop`（可选，平台停止策略时供收尾）；`on_tick` 为 P1 能力，MVP 不提供 | `on_bar`、`on_order`、`on_init` 为必须实现；回调契约见 ⑤ |

    **② 职责面：能力边界同时是责任边界（消灭"双方都不管"的地带）**

    | 关注点 | 策略（用户代码）负责 | SDK / 平台负责 |
    |---|---|---|
    | 手数归一化 | 传入期望手数（允许小数） | 按品种 `volume_step / min / max` 向下取整为合法手数，经 `on_order` 回传**实际**手数；不得因取整而改变交易方向 |
    | 保证金充足性 | 无需自检 | 强制校验（**回测中同样执行**）；不足则返回结构化错误码，策略可捕获后继续 |
    | 退出逻辑（止盈止损） | **全部由策略自行实现**（在 `on_bar` 中判断并平仓；tick 级退出逻辑随 `on_tick` 于 P1 提供） | MVP 不下发券商侧保护单——编辑器模板与文档须明示该风险：**策略崩溃或网关断线期间，持仓无任何保护** |
    | 交易时段 / 假期 | 无需判断 | 仅在可交易时段发单；非交易时段返回 `MARKET_CLOSED` |
    | 网络重连 / 重试 | 无感知 | SDK 内部处理；**重试不得造成重复下单**（幂等由平台保证） |
    | 未来数据防护 | 无 | 平台保证任何历史访问被自动截断至当前时刻（见 ⑤） |
    | 可复现性 | 需要随机性时使用 SDK 提供的随机源 | 回测运行时固定随机种子并记入报告 |
    | 品种与参数声明 | 在 `on_init` 中声明品种、周期、参数默认值 | 平台据此校验越权访问；**未声明即拒绝** |

    **③ 隔离面：运行期拦截的禁止清单（含已知逃逸面的显式处置）**

    **越界处置（唯一口径）**：拦截该次调用 → 返回结构化错误码 → 记入审计日志并标记策略"越界"；**直接触及隔离边界的**（如尝试建立网络连接、非法 import）立即终止策略并告警。

    - **网络访问**：`socket` / `ssl` / `http` / `urllib` / `requests` / `ftplib` / `smtplib`
    - **文件系统**：`open` / `os` / `io` / `pathlib` / `shutil` / `tempfile` / `mmap`
    - **子进程与系统调用**：`subprocess` / `ctypes` / `sys` / `signal` / `atexit`
    - **并发**：`threading` / `multiprocessing` / `asyncio` / `concurrent` / `queue`——回测必须单线程确定性执行
    - **反射与动态执行**：`importlib` / `pickle` / `marshal` / `eval` / `exec` / `compile` / `__import__`
    - **真实时钟**：`time` / `datetime.now` / `datetime.utcnow`——时间一律取自 `ctx`（见 ⑤）
    - **标准库白名单（逐项授予）**：`math` / `statistics` / `datetime`（不含 `now`、`utcnow`）/ `decimal` / `collections` / `itertools` / `functools` / `dataclasses` / `enum` / `typing` / `json` / `re` / `string` / `copy` / `random`（种子由平台固定）
    - **第三方库白名单**：MVP = `numpy` / `pandas` / `scipy`（版本随 SDK 钉死，见 ⑥）；sklearn 等按申请评审加入（P1）
    - **第三方库的逃逸面必须显式处置**（仅禁 `open` 无效）：`pandas.read_csv` / `read_pickle` / `HDFStore`、`numpy.load` / `save` 等**文件入口禁止**；`pandas.read_html` / `read_json` 等 **URL 入口禁止**；`numpy` 的 BLAS 线程数**固定为 1**（保证确定性，见 ⑤）
    - **策略间通信** / 访问其他策略的 `storage`

    **实现要求**：白名单 `import` 钩子（非黑名单屏蔽）+ 独立子进程。**禁止清单是最小要求（实现可加严）；授予清单是封闭集合（只减不增）**。钩子以"策略顶层可 import 的模块"为单位判定——第三方库（numpy / pandas / scipy）**自身的内部依赖不受此限制**（否则它们无法加载），但其对外暴露的逃逸入口必须按上一条逐一处置，这是实现中最容易被漏掉的一环。
    **失控循环**：沙箱不提供 `sleep`，一切无限循环由 ④ 的执行超时熔断处置。

    > **威胁模型分期（决定安全投入强度）**：Phase 1 为单租户私有化部署，策略即用户自己写的代码——沙箱目标是**防误伤**（bug、死循环、失控下单破坏平台与账户），不对抗蓄意攻击；Phase 3 SaaS 化后策略可能来自第三方，届时应升级为**防恶意**，并完成独立安全评审与对抗性渗透测试。两阶段实现架构（子进程隔离 + import 钩子）保持兼容，避免返工。

    **④ 运行面：资源与时限（超限处置必须唯一且可预期）**

    | 维度 | 回测 | 模拟 / 实盘 | 超限处置 |
    |---|---|---|---|
    | 单次回调时长 | ≤ 5s | ≤ 1s | **终止策略** + `RESOURCE_TIMEOUT` |
    | `on_init` 时长 | 计入回测总时长 | ≤ 60s（允许加载模型 / 预热） | 终止策略 |
    | 进程内存 | ≤ 512MB | ≤ 512MB | **终止策略** + `RESOURCE_EXCEEDED` |
    | 单 bar 下单调数 | ≤ 20 | ≤ 20 | **拒单**（返回 `RATE_LIMITED`，策略可继续）+ 告警；连续触顶由风控中心（M6）升级处置 |
    | `ctx.storage` 写入 | ≤ 1MB | ≤ 1MB | 写入失败并返回错误码，策略可继续 |
    | 日志条数 | — | — | 超限丢弃并在日志中注明丢弃条数，**不终止**策略 |
    | 回测任务总时长 | ≤ 10min | — | 终止任务，报告标记超时 |

    **超限处置的唯一分类原则**（消除"拒单还是杀策略"的歧义）：

    - **安全性超限**（执行超时、内存超限、沙箱越界、非法 import）→ **终止策略**，返回明确错误，实盘同时告警；终止前触发 `on_stop`（若已定义）供策略收尾。
    - **业务性拒绝**（保证金不足、风控拦截、市场关闭、重新报价、频率超限、storage 满）→ **返回结构化错误码，策略继续运行**；不得静默失败，不得向策略抛出不可捕获异常。
    - 两类在三态中返回**同一套错误码**，差异仅在于实盘额外触发告警。

    **⑤ 一致性面：三态差异显式化 + 未来数据与确定性硬契约**

    差异**只允许**存在于下表，其余一切行为三态一致（API 面完全一致，策略代码零修改跨三态运行）：

    | 行为 | 回测 | 模拟 | 实盘 | 策略是否感知 |
    |---|---|---|---|---|
    | 下单 → 成交时序 | 同 bar 内同步触发 `on_order` | 异步 | 异步 | 否（K 线级回测） |
    | `on_tick`（P1） | 不调用 | 真实 tick | 真实 tick | 是，文档明示 |
    | 成交价 | 由撮合档位决定 | 实时行情撮合 | 券商真实成交 | 否（仅报告呈现） |
    | 历史回看窗口 | 有界（≤ 5000 根） | 无界 | 无界 | 是 |
    | 拒单来源 | 模拟风控 + 保证金 | 同左 + 真实点差 | 券商 + 平台风控 | 否（同一错误码枚举） |

    表中 `on_tick` 为 P1 口径；MVP 一律 bar 驱动（三态均不调用），该能力随 Tick 数据管理（P1）引入。实时报价推送（买卖价 / 点差）不受影响——模拟盘撮合与实时行情展示依赖它，属于行情链路而非策略回调。

    - **时间语义（必须唯一）**：`ctx` 暴露的一切时间均为 **UTC**；bar 的 `time` 为**开盘时间**，且该 bar 仅在**收盘后**才对 `on_bar` 可见。券商服务器时间仅作为账户信息中的只读字段提供，不参与策略逻辑。
    - **未来数据契约（回测可信度的地基）**：回测中任何历史 / 报价访问由 SDK 自动截断至当前 bar 收盘时刻，SDK 不提供任何访问未来数据的入口，策略无需也无法自行防护。报告中若出现"存在未来数据访问"，按**最高优先级缺陷**处理。
    - **确定性契约**：同一策略代码 + 同一参数 + 同一数据 + 同一 SDK / 环境版本 ⇒ 逐笔可复现。为此：随机种子固定、BLAS 线程固定为 1、策略不可见真实时钟、回测中禁止依赖任何进程外状态。
    - **回调契约**：`on_bar` **在预热期同样被调用**（策略可据此累积指标状态，但预热期下单由平台拒绝）；回调抛出异常 → **终止策略**并保留完整堆栈（不再静默跳过）；`on_order` 在回测中于 `ctx.buy()` 调用栈内重入触发，**回调内允许再次下单**；平台"暂停 / 停止"通过 `on_stop` 通知策略收尾。

    **⑥ 演进面：版本与环境**

    - SDK 语义化版本；minor 只增不改，破坏性变更需 major + **6 周弃用公告期**。
    - **运行环境随 SDK 钉死**：`numpy` / `pandas` / `scipy` 的版本纳入 SDK 兼容承诺，随 SDK 整体升级（否则宿主 numpy 1.x → 2.x 的破坏性差异会使"可复现"承诺落空）。策略元数据记录 `SDK 版本 + 环境依赖版本 + 数据版本`，保证回测报告可复现历史口径。
    - 弃用接口在编辑器内以删除线提示并给出替代写法，弃用期内旧接口行为不变。

    **⑦ 非目标（明示不做，管理预期）**

    - 不是通用 Python 运行时（不承诺任意 pip 包可用）；深度研究 / 机器学习训练走 Jupyter 笔记本（P1），notebook 产出信号、SDK 负责执行——研究与执行分离。
    - MVP 不提供券商侧保护单、限价 / 止损单、追踪止损（P1）。
    - 不提供策略间通信、组合级共享状态、跨账户操作。

    > 交付物要求：Phase 1 开发启动前，由量化负责人与后端共同输出《SDK v1 API 规范》详设文档。该文档必须**逐行覆盖本文 ①~⑦ 的每一项**（每个接口的签名、参数、返回值、错误码全表与超限行为），并将 ② 职责面落实为可测的验收用例。**本 PRD 锁定能力边界与契约原则，规范文档只做展开，不得放宽边界。**

- **安全（P0 硬要求）**：策略代码在独立子进程沙箱中执行——白名单 `import` 钩子（非仅黑名单屏蔽）+ 上述资源限额 + ③ 的逃逸面处置。Phase 1 以"防误伤"为目标（见 ③ 威胁模型分期），沙箱逃逸按**最高级安全缺陷**处理

#### M4 回测中心
- **回测配置**：品种（MVP 单品种）、周期、时间范围、初始资金、杠杆、点差模式（当前点差/固定点差/真实点差 P1）、手续费、滑点模拟、隔夜利息（P1）
- **撮合模式（三档，用户可切换，报告页显著标注所用档位）**：

  | 档位 | 成交价 | 滑点 | 定位 |
  |---|---|---|---|
  | 保守（默认） | 次根 K 线开盘价 ± 保守滑点 | 固定加成 | 防未来函数，贴近最差可执行情形 |
  | 标准 | 当根收盘价 + 实时点差 ± 中等滑点 | 按品种点差比例 | 与 MT5 原生测试器口径最接近 |
  | 乐观 | 当根收盘价，无滑点 | 0 | 仅用于策略逻辑验证，报告加醒目水印提示不可作为实盘预期 |

- **预期落差管理（P0，与撮合模式配套）**：
  - **提交前显性确认（P0）**：回测配置页在提交任务前展示本次撮合档位的成交价构成假设（基准价 + 点差口径 + 滑点参数），选择「乐观」档需二次确认并显示风险提示「结果不具备实盘参考意义」；档位与假设快照随任务永久记录
  - **成交透明化**：报告内每笔交易展示成交价构成（基准价 + 点差 + 滑点 + 手续费），并提供「假设说明」浮层，明确解释与 MT5 原生策略测试器的口径差异
  - **原生测试器口径锚定（对账的第三方参照）**：保守档 ↔ 原生「仅开盘价」模式（同为"次根开盘价"逻辑，天然适合低容差逐笔对账）；标准档 ↔ 原生「1 分钟 OHLC」模式（口径最接近）。交易明细已支持 CSV 导出，用户可导入原生测试器自行复核——平台不垄断口径解释权，该锚点同时服务于回测引擎的回归测试（§7 #4）
  - **成交敏感性指标**：一键生成「保守 vs 标准」双报告，输出收益率差值；差值超过阈值（如年化 5%）时标记 ⚠️「策略对执行价格敏感，实盘表现可能显著低于回测」——把落差转化为风控信号而非信任危机
  - **真实滑点校准（P1）**：模拟/实盘运行期统计该账户实际成交滑点，自动回写为该账户回测的默认滑点参数，使回测口径随使用逐步收敛于用户真实环境
  - **回测-实盘偏差报告（P1）**：策略转实盘后，持续对比同期信号的理论成交与实际成交，量化偏差来源（滑点/点差/延迟）
- **产品原则**：默认档位保守不可被静默更改（新建回测可改，但报告永久记录档位）；宁可用户抱怨"回测偏悲观"，不可出现"回测偏乐观导致实盘亏损"——前者可解释，后者不可逆
- **报告内容**：
  - 核心指标：总收益率、年化、最大回撤、夏普、索提诺、胜率、盈亏比、交易次数、平均持仓时长
  - 图表：权益曲线 vs 基准（买入持有）、回撤区间图、月度收益热力图
  - 明细：每笔交易（开平仓时间/价格/手数/盈亏/滑点成本），支持导出 CSV
  - 日志：策略 print 输出与信号标记（在 K 线图上标注买卖点）
- **任务机制**：回测异步执行，队列排队，页面显示进度；单任务超时 10 分钟自动终止

#### M5 模拟 & 实盘交易
- **模拟盘**：策略绑定实时行情 + 虚拟资金，撮合逻辑与回测一致（同一套代码），支持随时重置
- **实盘准入闸门（灰度约束的产品化固化，P0 硬要求）**

  > **设计原则**：「灰度期强制先完成回测、再跑模拟盘」不能只作为风险对策存在于 §7 的纸面承诺，必须成为系统的强制分支——**任何可由人工酌情绕过的闸门视为未实现**。闸门以「策略版本 × MT5 账户」为判定维度。

  | 闸门 | 规则 | 不满足时的处置 |
  |---|---|---|
  | ① 权限闸 | 实盘能力由平台功能开关（feature flag）控制，灰度期仅对种子用户开放（发行/激活时启用）；未授权时「交易」页不显示实盘入口，且**后端接口同样拒绝**（前端隐藏不算权限） | 无实盘入口，界面明示"未开放" |
  | ② 回测闸 | 该策略（**与拟部署完全相同的版本**）已在平台内完成 ≥ 1 次**成功回测**（存在可查报告，含配置快照；报告业绩好坏不作放行条件） | 部署向导拦截，指引去回测中心 |
  | ③ 模拟时长闸 | 该策略（与拟部署完全相同的版本）已在目标账户连续模拟运行 ≥ 14 天（默认值，可配置范围 7~60，修改记入审计）；**策略版本变更 → 回测闸与时长计时一同清零** | 部署向导拦截 |
  | ④ 记录闸 | 模拟运行期间无风控触发记录、无沙箱越界记录（Phase 2 对账能力上线后，对账异常一并纳入） | 部署向导拦截 |

  - **不满足处置（唯一口径）**：向导准入检查步逐条显示四闸的通过/不通过与原因；补救方式只有补齐对应前置（回测闸：完成一次成功回测；时长/记录闸：继续模拟），**不提供任何绕行路径**（含高级模式、后台改数、API 直调）
  - **决策信息**：准入通过时向导同屏展示回测报告摘要与模拟期报告（权益曲线/回撤/夏普/交易笔数）供用户确认；报告好坏本身不作放行条件（避免阈值主观化）——回测闸只要求「完成过成功回测」，不要求「业绩好」
  - **审计**：每次放行记录指标快照（权限来源、回测报告摘要、模拟天数、违规记录）入审计日志，字段与防篡改规范见 M7
- **实盘部署**：
  - 部署向导：选策略版本 → 选 MT5 账户 → **准入检查（四闸：权限/回测/模拟时长/记录）** → 分配资金/手数上限 → 设置风控规则（强制，不可跳过）→ 免责条款勾选 + 二次确认（输入账户尾号，均不可跳过）→ 启动；风控规则步须显著披露：**平台风控依赖网关在线，掉线期间持仓无保护**（叠加 MVP 无券商侧保护单，见 M6 风险真空处置）
  - **观察期（阶梯放量）**：首次实盘启动后前 7 天（默认）强制保守上限——手数上限默认为品种最小手数、资金上限默认为分配资金的 10%（二者均可调低、不可调高）；观察期满且期间无风控触发，才可在向导中提升至完整配额（需二次确认）；观察期内触发「当日停止开仓」及以上 → 观察期计时清零；触发「全平仓+停止策略」级规则 → 直接自动降级（见 M6）
  - 运行控制：启动/暂停（不再开新仓）/停止（可选平仓）三态；**状态恢复契约**：停止后重启的策略仅恢复 `ctx.storage`，其余内存状态由 `on_init` 重建（三态一致，启动前界面明示，契约见 M3 ①）
  - 状态页：策略运行状态、当前持仓、今日盈亏、最近信号、**准入与观察期状态（剩余天数/当前上限）**、运行日志（准实时，≤3s 延迟）
- **一致性原则**：回测、模拟、实盘必须使用同一策略代码与同一撮合内核——回测与模拟盘共用引擎、仅数据源与时钟不同，实盘仅执行器边界不同，这是产品可信度的生命线；该原则由三态对账回归作为发布门禁守护（§7 #4）

#### M6 风控中心
- **账户级规则**（触发即执行动作）：
  - 单日最大亏损（金额/百分比）→ 当日停止开仓
  - 最大总回撤 → 全部平仓 + 停止策略
  - 单笔最大手数 / 最大持仓数 / 最大同向敞口
  - 下单频率限制（防策略死循环刷单）
- **Kill Switch**：首页常驻红色按钮，点击后：撤销全部挂单 → 平掉全部持仓 → 停止全部策略 → 通知用户；需要二次确认，全过程 ≤ 3 秒
- **对账**：每 5 分钟将平台记录的持仓与 MT5 实际持仓核对，不一致立即告警并冻结该账户自动交易
- **自动降级（灰度的产品化执行）**：实盘策略触发「全平仓 + 停止策略」级规则（最大总回撤、Kill Switch）即被平台自动降级——撤销其实盘执行资格，回退为「仅可模拟」；对账能力（P1）上线后，对账不一致同样触发降级。降级**不自动恢复**：须在风控中心走人工复核 + 二次确认，并产生审计记录；降级与恢复均触发告警
- **闸门输入**：模拟运行期间的风控触发记录实时同步给 M5 准入闸门的记录闸，作为放行依据
- **网关掉线风险真空处置**：平台风控在网关侧执行——网关离线 = 实盘持仓进入「无平台风控保护」状态；叠加 MVP 不提供券商侧保护单（见 M3 ②），掉线期是**双重风险真空**。处置：离线超过 5 分钟（默认，可配置）→ 经全部可用渠道通知用户「实盘持仓当前无保护」；恢复连接后 → 先对账、将离线期间持仓差异作为告警呈现 → **由用户人工决策，平台默认不自动平仓**（行情已陈旧，自动动作可能造成更大损失）

#### M7 监控与告警
- **仪表盘（登录后首页）**：账户净值与今日盈亏（大数字）、权益曲线（当日分时）、持仓列表、运行中策略卡片（状态灯）、网关健康状态、告警滚动条
- **告警事件**：成交、开平仓、风控触发、网关断线、策略异常退出、回撤阈值、**审计链校验失败**
- **MVP 渠道**：站内 + 邮件；P1 加 Telegram Bot / 钉钉 / 企业微信 Webhook
- **审计日志（P0 硬要求）**

  > **定位**：审计日志是「发生了什么、谁做的、系统有没有拦住」的唯一取证依据——任何资金或安全争议发生后，它是第一份被查阅的材料。**审计缺失 = 责任无法界定**，按与风控失效同级的缺陷处理。

  **① 记录范围（封闭清单——写操作必留痕）**

  | 类别 | 事件 |
  |---|---|
  | 账户与凭据 | 登录/登出（含 2FA 结果）、网关绑定/解绑、凭据变更、只读↔交易模式切换 |
  | 策略生命周期 | 创建/编辑/版本冻结、回测提交、模拟启动/重置、**准入闸门放行（附指标快照）**、实盘启动/暂停/停止、降级/恢复（附复核意见） |
  | 交易行为 | 每笔信号→订单→成交/拒单（拒单含错误码与风控判定）、手动下单/撤单/平仓 |
  | 风控事件 | 规则触发及执行的动作、Kill Switch 触发、对账不一致与冻结/解冻 |
  | 配置变更 | 风控规则与灰度参数变更（**记录旧值→新值**）、权限开关变更 |
  | 沙箱事件 | 越界拦截、非法 import、资源超限终止 |
  | 系统 | 网关连接/断开/重连、审计链完整性校验结果 |

  凡能改变资金、权限或系统行为的 API 都必须产生审计记录；清单覆盖缺失按最高优先级缺陷处理。

  **② 记录字段（每条最小集）**：UTC 毫秒时间戳（时间语义与 M3 ⑤ 一致）｜ 行为主体（用户 / 系统 / 策略 + 策略 ID + 版本）｜ 动作类型（封闭枚举）｜ 目标对象（账户 / 品种 / 策略）｜ 动作参数与结果（成功/失败 + 错误码）｜ 风控判定（放行/拒绝 + 规则 ID）｜ 来源（IP / 会话）｜ 关联 ID（信号→订单→成同一链路可串联）

  **③ 防篡改（Write-Once）**
  - 只追加写入，**不存在**删除或修改接口，平台管理员同样无修改权限
  - 哈希链：每条记录包含前一条的哈希，任何篡改/删节可被校验发现；提供一键全链或按范围的完整性校验页
  - 版本升级与数据迁移必须保持链的连续性

  **④ 留存、导出与查询**
  - 在线默认留存 1 年（可配置），更早数据自动归档至本地；导出支持 CSV/JSON，**导出行为本身也记入审计**
  - 查询页：按时间 / 主体 / 动作类型 / 账户 / 策略过滤；任一告警事件可关联下钻到原始审计记录；提供事故复盘时间线视图（单时间点回看前后全部事件）
  - 策略运行日志（print / `ctx.log`）不属审计——量大价值低，单独存储；审计只收结构化事件

## 5. 技术架构建议（供研发评审，产品视角约束）

### 5.1 MT5 接入方案对比（关键决策）

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 官方 `MetaTrader5` Python 包 | Python 进程直连本机 MT5 终端 | 官方支持、API 全（行情+交易）、开发最快 | 网关必须与 MT5 终端同机(Windows)；每终端单连接 | ✅ **MVP 首选** |
| B. MQL5 EA 桥接（ZeroMQ/WebSocket） | 在 MT5 里跑 EA，转发指令 | 可穿透复杂网络、可做 tick 级推送 | 开发维护成本高、EA 稳定性依赖终端设置 | 备选/Phase 2 补充 tick 推送 |
| C. MT5 Manager API | 券商级管理接口 | 多账户集中管理 | 需要券商授权，个人拿不到 | ❌ 放弃 |

**产品约束**：MVP 提供「MT5 网关」Windows 安装包（内嵌 Python 服务 + 官方 MetaTrader5 包），用户装在与 MT5 终端同一台机器上，扫码/输入配对码与 Web 服务绑定。云部署版由我们托管网关（用户需提供 MT5 账号）——托管模式的凭据安全方案需单独安全评审。

**结构性约束声明（Windows 依赖，不回避）**：MT5 终端仅有 Windows 版，官方 `MetaTrader5` API 要求同机进程通信——自部署模式下「Windows 常开 + 终端保持登录」是**不可消除的前提**，产品只能降低运维负担、管理其风险，不能承诺消除。分阶段缓解路线：

- **Phase 1**：服务常驻 + 看门狗保活 + 电源预检 + 一键自检 + 掉线风险真空告警（见 M1 / M6），把「保持网关活着」做到接近零运维
- **Phase 2**：方案 B（EA 桥）可用轻量 EA 替代自建 Python 服务、降低同机耦合，但终端仍须在 Windows 上常开——缓解而非消除该约束
- **托管模式**：唯一能根本免除用户运维的路径，但等于接受凭据托管——**Phase 1 明确不启用**；启用前置条件为完成安全评审（凭据加密白皮书 + 渗透测试）与资金安全责任边界的法务评审（见 §7 风险 #3）

### 5.2 总体架构

```
浏览器 (React + TradingView Lightweight Charts / klinecharts)
   │ HTTPS / WSS
   ▼
Web 后端 API (Python FastAPI)
   ├── PostgreSQL        —— 用户/策略/回测结果/风控规则/审计
   ├── TimescaleDB(或ClickHouse) —— K线/Tick 时序数据缓存
   ├── Redis             —— 实时报价推送、会话、任务队列 broker
   └── Celery/RQ Worker  —— 回测执行(沙箱子进程)、参数优化并行
   │ gRPC/WebSocket(加密, 配对证书)
   ▼
MT5 网关节点 (Windows, 与 MT5 终端同机)
   └── MetaTrader5 Python API → MT5 Terminal → 券商服务器
```

- **回测引擎**：MVP 自研**单一**轻量事件驱动内核——回测与模拟盘共用同一套撮合 / 持仓 / 风控 / 回调代码（同内核，仅数据源与时钟不同：回测喂历史 bar、模拟喂实时 bar），实盘仅以最小执行器边界（市价下单 + 回报）接入；「三态一致」由**同内核 + 三态对账回归**保证（发布门禁，见 §7 #4），而非三套引擎各自对齐。不改造现成开源引擎（freqtrade / backtrader / vn.py 等）：其撮合与策略 API 均为加密资产或期货语义，CFD 的点值 / 手数步长 / 保证金规则需重写，且 backtrader 长期停更、vn.py 对 MT5 仅行情支持——适配成本不低于自研，还丧失了对撮合三档口径的控制权。P1 引入 vectorbt 仅作参数粗筛的加速工具：结果为近似值、**不参与三态一致承诺**，最终结论一律以事件引擎为准
- **实时链路**：网关推送 tick/报价 → Redis pub/sub → WSS → 前端，端到端目标 ≤ 500ms
- **部署形态**：Docker Compose 一键部署（Web 侧）+ Windows 网关安装器

### 5.3 非功能性需求

| 类别 | 要求 |
|---|---|
| 性能 | 单用户场景：页面首屏 ≤ 2s；K线加载 ≤ 1s；回测并发 ≥ 4 任务 |
| 可用性 | 实盘交易时段（5×24 外汇）网关断线自动重连，重连 ≤ 30s；离线超 5 分钟触发风险真空全渠道告警（见 M6）；平台重启不影响网关侧已运行的风控规则 |
| 安全 | 全链路 TLS；MT5 凭据加密存储；策略沙箱；操作审计日志防篡改（只追加 + 哈希链，规范见 M7）；登录 2FA |
| 合规 | 页面明示「本平台为工具软件，不构成投资建议」；不提供代客理财/信号订阅功能；用户协议中界定资金安全责任边界 |

## 6. 路线图

### Phase 1 — MVP（约 6~8 周）
> 目标：跑通「绑账户 → 看行情 → 写策略 → 回测 → 模拟盘」最小闭环，实盘仅对种子用户灰度（**由准入闸门 + 功能开关固化执行，见 M5，不依赖口头约定**）

- 用户登录、MT5 网关绑定（只读+交易两级）、网关服务常驻/看门狗/电源预检/一键自检（见 M1）
- 行情中心（品种/报价/K线图/历史数据同步；K 线为主，tick 级数据 P1）
- Web Python 编辑器 + SDK v1（5 个模板）+ 沙箱执行
- 回测（单品种、事件驱动、三档撮合模式、完整报告页、成交敏感性对比）
- 模拟盘、基础风控三规则（日亏/总回撤/单手数）、Kill Switch
- **实盘准入闸门（权限/回测/模拟时长/记录四闸）+ 灰度功能开关 + 观察期 + 自动降级**
- 仪表盘 + 站内/邮件告警 + 审计日志（只追加 + 哈希链防篡改，见 M7）
- **验收标准**：种子用户（5~10 人）能独立完成一次完整用户旅程，回测结果与手工计算对账误差 < 1%；**准入闸门绕行 = 0**——任何不满足四闸的实盘尝试（含 API 直调）必须被拦截，以回归测试用例覆盖；**三态对账回归入 CI 发布门禁**——同一段历史行情回放，回测 vs 模拟盘逐笔一致（一致 = 通过，差异 = 缺陷而非容差）；黄金策略在 MT5 原生测试器（保守档 ↔ 仅开盘价模式）对账误差 ≤ 阈值，任一失败即发布阻断

### Phase 2 — 实盘强化（约 6 周）
- 实盘部署向导 + 多账户管理、手动交易面板
- 参数优化（网格）、Walk-Forward / 蒙特卡洛（防过拟合）、回测对比、数据质量检查、Tick 数据
- Telegram/钉钉/企微告警、持仓对账、策略版本管理
- 隔夜费/手续费精细建模

### Phase 3 — 规模化（视验证结果）
- 多租户 SaaS 化、配额与计费
- 可视化策略构建器、组合回测
- 策略市场（仅工具分享，不涉及信号售卖，需法务评审）

### MVP 团队配置建议
后端 ×2（含网关）、前端 ×1.5、量化/回测引擎 ×1、产品 ×0.5、设计 ×0.5、测试 ×0.5

## 7. 风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | **资金安全**：实盘 bug 导致用户亏损 | 🔴 极高 | 风控默认开启且不可跳过；**灰度约束已固化为产品功能，不再是纸面对策**：实盘准入闸门（权限/回测/模拟时长/记录四闸）+ 观察期阶梯放量 + 自动降级（见 M5/M6）；对账机制；赔付/免责条款法务评审 |
| 2 | **合规**：被认定为投资咨询/配资业务 | 🔴 高 | 严格定位工具软件；不做信号售卖/带单/资管功能；上线前法律咨询（尤其面向中国大陆用户的展业边界） |
| 3 | MT5 凭据托管的信任问题 | 🟠 中高 | 优先推私有化部署（凭据不出用户机器）；**托管模式 Phase 1 明确不启用**，启用前必须完成凭据加密安全评审（白皮书 + 渗透测试）与资金安全责任边界的法务评审；只读模式降低暴露面 |
| 4 | 回测与实盘结果差异大，口碑崩塌（含用户拿报告对比 MT5 原生测试器对不上） | 🟠 中高 | 三态一致架构（同内核 + 三态对账回归为发布门禁，见 M4/M5）；三档撮合模式透明可切换 + 与原生测试器口径锚定；成交成本逐笔展示 + 口径差异说明；成交敏感性预警；真实滑点自动校准闭环（见 M4 预期落差管理） |
| 5 | 券商 MT5 版本/配置差异导致网关不稳定 | 🟡 中 | 建立券商兼容性矩阵；网关版本化 + 远程日志诊断；社区反馈通道 |
| 6 | 策略沙箱被绕过 | 🟡 中 | 白名单 import 钩子、子进程隔离、资源限额、③ 中的逃逸面处置；Phase 1 按"防误伤"验收，SaaS 化（Phase 3）前须完成防恶意加固与专项渗透测试 |
| 7 | **用户侧环境单点故障**：用户 Windows 关机/休眠/断网导致交易中断，且平台风控随之失效（风险真空） | 🟠 中高 | 承认这是自部署模式的结构性约束（见 §5.1）：服务常驻 + 看门狗 + 电源预检降低发生概率（M1）；离线超阈值全渠道告警 + 恢复后对账不平仓（M6）；部署向导显著披露真空期（M5）；长期解为托管模式（需先过安全评审，见 #3） |

## 8. 待决策问题（需创始人/决策者拍板）

1. **商业模式**：私有化买断制、订阅制 SaaS，还是先自用后开源？——直接影响多租户与计费的架构投入时机
2. **托管 vs 自部署优先级**：MVP 先做哪种网关部署形态？（建议：**MVP 只做自部署**——信任成本低、依赖少；托管模式的启用条件是安全评审通过而非排期承诺，见 §7 风险 #3）
3. **策略语言**：MVP 只做 Python，还是同时兼容导入 MQL5 EA？（建议：只做 Python，MQL5 兼容成本高）
4. **目标市场**：中国大陆用户为主（需考虑网络与合规环境）还是海外华人/全球？影响告警渠道（微信 vs Telegram）与合规策略
5. **灰度参数默认值**：产品建议——准入模拟时长 14 天、观察期 7 天、观察期资金上限 10%（均可后台配置、修改留审计）；需确认与种子用户灰度节奏及风险偏好的匹配度
